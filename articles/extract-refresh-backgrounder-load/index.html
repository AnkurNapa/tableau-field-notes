Extracts and backgrounder load

When every refresh is scheduled for 02:00, the backgrounder queue does the rest. Measure queue wait from the repository or Admin Insights, then fix it with staggered schedules, incremental refresh and only then more capacity.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 3 Ankur Napa ServerCloudPerformanceAPICertification

Short answer

A backgrounder runs one job at a time: an extract refresh, a subscription, a flow run, a data-driven alert. When 60 refreshes are scheduled for the same minute and two backgrounders are free, 58 of them wait. Users do not see the wait. They see yesterday's numbers at 07:00 and lose faith in the dashboard.

Fix it in this order. Spread the schedules. Make the big sources incremental. Stop refreshing content nobody opens. Add backgrounder capacity last, because capacity is the only fix that costs money every month. On Tableau Server you control the backgrounders. On Tableau Cloud you control only the schedules and the extract design, inside limits Salesforce sets.

The symptom

Harbour Goods schedules every extract at 02:00 because 02:00 was the default someone picked in 2023. The store scorecard reads from the certified orders source. Some mornings it shows yesterday. Some mornings it is fine. The refresh never fails. It just finishes late.

Measure it

On Tableau Server: background_jobs

The repository table background_jobs holds one row per job with created_at (queued), started_at, completed_at, finish_code (0 success, 1 failure, 2 cancelled), job_name and backgrounder_id. Queue wait is started_at minus created_at. With repository access enabled, connect to workgroup on port 8060 as readonly:

SELECT date_trunc('hour', created_at)                                       AS hour_queued,
       COUNT(*)                                                             AS jobs,
       ROUND(AVG(EXTRACT(EPOCH FROM (started_at - created_at)) / 60)::numeric, 1)  AS avg_wait_min,
       ROUND(MAX(EXTRACT(EPOCH FROM (started_at - created_at)) / 60)::numeric, 1)  AS max_wait_min,
       ROUND(SUM(EXTRACT(EPOCH FROM (completed_at - started_at)) / 60)::numeric, 1) AS run_min,
       SUM(CASE WHEN finish_code = 1 THEN 1 ELSE 0 END)                     AS failed
FROM background_jobs
WHERE job_name IN ('Refresh Extracts', 'Increment Extracts')
  AND created_at > NOW() - INTERVAL '7 days'
GROUP BY 1
ORDER BY 1;

Run SELECT DISTINCT job_name FROM background_jobs first to confirm the names on your version. Timestamps are stored in UTC, so 02:00 in Bengaluru is 20:30 the previous day in this table.

The admin view Background Tasks for Extracts shows the same thing without SQL.

On Tableau Cloud: Job Performance and the REST API

Open the Admin Insights project and connect to Job Performance, which lists background job runs such as extract refreshes and flow runs. Plot queue time against the scheduled hour.

On either platform, the REST API lists jobs. This call returns extract refresh jobs:

curl -s "https://<server>/api/3.28/sites/<site-luid>/jobs?filter=jobType:eq:refresh_extracts" \
  -H "X-Tableau-Auth: <token>" -H "Accept: application/json"

And this one lists the scheduled refresh tasks, so you can see what is due when:

curl -s "https://<server>/api/3.28/sites/<site-luid>/tasks/extractRefreshes" \
  -H "X-Tableau-Auth: <token>" -H "Accept: application/json"

What the Harbour Goods queue showed

The two nights are in server-backgrounder-jobs.csv. It is synthetic, produced by a small queue simulation: 60 refresh jobs a night on two backgrounders, in the same columns as background_jobs. The night of 14 September 2026 is the "before" period. Summed in Python:

Median queue wait126.3 min

Jobs waiting more than 30 min51
Certified orders source finished04:05

Total running time was 337 minutes. The backgrounders were not slow. They were queued. The certified orders source sat in the queue for an hour and a half because jobs start in the order the scheduler picks them. It was not first.

Fix it

1. Spread the schedules

On Server, ask the admin for schedules every 15 or 30 minutes from 02:00 to 05:45 and give the business-critical one a higher priority. On Server, a lower priority number runs first. On Cloud, each refresh has its own schedule. Set the times so no more than a few start together.

2. Make the big sources incremental

In Desktop: Data > the source > Extract Data. Keep All rows, tick Incremental refresh and choose the column under Identify new rows using column, for example Order Date. Republish. Use a date range refresh if old rows can change. Run a full refresh weekly to catch everything incremental misses.

3. Stop refreshing what nobody reads

Take the stale list from Monitor usage and health and remove their schedules. A refresh for a workbook nobody opened in 90 days is pure queue.

4. Add capacity, on Server only

Backgrounder is single threaded, one job per instance. Tableau's guidance allows up to half the node's cores as backgrounder instances, with a warning that each job can use several threads:

tsm topology set-process -n node2 -pr backgrounder -c 4
tsm pending-changes apply

For a bigger split, set a node role so one node runs only extract refreshes. That role needs Advanced Management:

tsm topology set-node-role -n node2 -r extract-refreshes
tsm pending-changes apply

Node role changes restart the server. Plan a window.

On Cloud you cannot add backgrounders. Concurrent extract refreshes are capped by edition, up to 15 jobs per tenant on Standard and more on Enterprise and Tableau+, plus a daily budget of backgrounder hours per Creator licence.

Prove it

The night of 21 September 2026 in the same file is the "after" period. Schedules are spread over four hours and the four largest sources run incremental:

These figures are illustrative. They come from the synthetic sample, not a measured server. Notice the last row. Spreading the schedules moved the last finish later. That is fine while the business day starts at 07:00. It is the number to watch as the site grows.

Where this breaks

  • Time limits. Tableau Cloud cancels a single refresh at two hours and the limit is not configurable. Tableau Server cancels at backgrounder.querylimit, 7200 seconds by default, plus backgrounder.extra_timeout_in_seconds, 1800 by default.
  • Incremental drift. Incremental refresh adds rows. It does not see updates or deletes in old rows outside the refresh range. A schema change also forces a full refresh.
  • Subscriptions share the queue. A 07:00 subscription burst competes with late refreshes. Give subscriptions their own window or node role.
  • Cloud data behind a firewall. Refreshes through Tableau Bridge also queue on the Bridge clients. A pool with one client is a single lane.
  • The database is the bottleneck. Thirty refreshes hitting the same warehouse at once can be slower than ten. Watch the source system, not just Tableau.

On the brewhouse floor

A brewery's morning has its own queue. The packaging line OEE extract, the tank log and the sales depletions all refresh at the same hour because that is when the night shift ends. Stagger them, make the tank log incremental by reading timestamp and the production meeting at 08:00 sees the night's gravity readings instead of the day before's. The backgrounder was never the problem. The calendar was. See visualising packaging-line OEE for one of the dashboards waiting in that queue.
