Server topology and scaling

Size Tableau Server nodes and processes for two different kinds of load: people opening views now and backgrounders refreshing data later. Start from the documented minimums, separate the two loads and grow by measurement.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 4 Ankur Napa ServerPerformanceCertification

Short answer

Tableau Server carries two kinds of work that want different things. Interactive load is people opening and filtering views. It runs in VizQL Server, Application Server, Data Server and Cache Server. It wants low latency at 09:00. Background load is extract refreshes, subscriptions and flows. It runs in Backgrounder and wants throughput at 02:00. Most scaling problems come from letting the second starve the first.

This applies to Tableau Server only. On Tableau Cloud, Salesforce sizes the platform and you work inside the published capacity limits.

Start with one node that meets the production minimum. Move to three nodes when you need high availability, which is the documented minimum for it. Separate background work onto its own node when backgrounder queues start delaying the morning. Add nodes when measurements say so, not when the renewal comes round.

Reference design

The documented production minimum for a single node, for 2022.3 and later: 8 cores (16 vCPUs) at 2.0 GHz or higher, 128 GB RAM and 50 GB free disk. Earlier versions asked for less memory. Every node in a cluster should meet that, with exceptions: a dedicated Backgrounder node running up to two backgrounders may get by on 4 cores. A dedicated Prep Conductor node needs 4 cores and 16 GB. An independent gateway needs 2 cores, 8 GB and 100 GB of disk.

Rules behind the picture:

  • The initial node keeps a Backgrounder for all jobs in Tableau's baseline. Move it off when background work starts slowing interactive users.
  • Coordination Service runs as an ensemble of one, three or five. Three for three or four nodes. Three or five for five or more. Five is the maximum.
  • Repository runs active on one node with a passive copy on another. Move it off the initial node.
  • File Store runs on more than one node so extracts survive a node loss.
  • Backgrounder instances: up to half a node's cores. Each is single threaded.
  • Node roles split background work: extract-refreshes, subscriptions, flows, no-flows and others. Roles other than the default all-jobs and the flows role need Advanced Management. The flows role needs Data Management and Prep Conductor on that node.
  • File Store query roles extract-queries and extract-queries-interactive steer which nodes answer extract queries for subscriptions and for people. They also need Advanced Management.

The commands are short. The planning is not:

tsm topology set-process -n node3 -pr backgrounder -c 4
tsm topology set-node-role -n node3 -r no-flows
tsm pending-changes apply
tsm topology list-nodes -v

Node role changes restart the server.

Questions to ask the client

  1. How many people open a view between 09:00 and 10:00 on a Monday? What is the slowest view they open?
  2. How many extract refreshes, subscriptions and flows run? When do they run? What is the longest single refresh?
  3. What does an hour of downtime cost? Who decides when the server is down?
  4. Is there a load balancer team? Can it health-check the gateways?
  5. Are you licensed for Advanced Management or Data Management? Node roles depend on it.
  6. Will the nodes be physical, VMs or cloud instances? Are vCPUs dedicated or shared?
  7. Where do the databases sit relative to the nodes? Latency to a far warehouse looks like a slow server.
  8. Who runs upgrades? How long is the window?
  9. What does growth look like over two years: users, content or data volume?

Review checklist

  • Every node meets the documented minimum for the version installed.
  • Three or more nodes if high availability is a requirement. Two nodes are not highly available.
  • Coordination Service ensemble size matches the node count. Odd number, never more than five.
  • Repository active and passive on different nodes, off the initial node.
  • File Store on at least two nodes.
  • Backgrounder count per node is no more than half the cores.
  • A baseline is recorded before go-live: view load times, queue wait, CPU and memory per node.
  • Backups (tsm maintenance backup) run on a schedule and a restore has been tested on a separate server.
  • The upgrade has been rehearsed on a non-production cluster.

Anti-patterns

  • Undersized VMs. Running production on 4 vCPUs and 32 GB because the hypervisor team said so. It works until Monday at 09:00.
  • Everything on every node. Default process counts copied to all nodes, so backgrounders fight VizQL for the same cores.
  • Adding nodes to fix a slow workbook. A view that runs 40 queries per load is slow on any hardware. Fix the workbook first.
  • An even ensemble. Two Coordination Service instances give you no quorum benefit and one more thing to fail.
  • No measurement. Sizing by user count alone. Five hundred Viewers who read a subscription email cost less than fifty Creators refreshing hourly.

On the brewhouse floor

A brewhouse is sized the same way: by the peak, not the average. You do not buy a bigger mash tun because the weekly volume grew. You buy it because Monday's double brew no longer fits. Size the Tableau nodes for the Monday morning reporting peak and the 02:00 refresh peak separately. Keep them apart the way you keep the hot side and the cold side apart. Mixing them is where both go wrong.
