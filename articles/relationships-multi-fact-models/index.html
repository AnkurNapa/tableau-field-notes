Relationships and multi-fact models without double counting

Relate orders to products and stores, add a targets table at a different grain, then join it the old way and watch sales inflate twelvefold. Learn when a join or a blend is still the right call.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 2 Ankur Napa DesktopCertification

Short answer

A Tableau data source has two layers. The logical layer holds tables linked by relationships, the flexible noodles. Each logical table can contain a physical layer where tables are joined or unioned into one. Relationships keep every table at its own grain and only join at query time, for the fields the view uses. That is why a targets table by store and month can sit next to an orders table without inflating either. Joins merge rows before any question is asked, so a one-to-many join duplicates the many side. Since version 2024.2 you can also give a model more than one base table, which is Tableau's multi-fact model for two fact tables that share dimensions. Blends are the last resort, mostly for published data sources that cannot be related.

What you will build

  • A relationship model: orders related to products and to stores.
  • A second fact table, monthly targets by store and category, added two ways: as a branch off stores, then as a second base table.
  • The same targets joined physically, to see the double counting with your own eyes.

Before you start

  • Tableau Desktop 2024.2 or later for the multi-fact step. Earlier versions can do everything else.
  • Download the cleaned Harbour Goods orders (55 orders, the 60-row sample less its five deliberate faults), products, stores and store targets. The targets file has 72 rows: six stores, four categories and three months, with a target_sales column.

Steps

1. Relate orders, products and stores

  1. Select Connect > To a File > Text file and choose the orders file. It lands on the canvas as the first table.
  2. Drag the products file from the left pane onto the canvas. A noodle appears and the Edit Relationship pane opens. Check the pair reads product_id = product_id.
  3. Drag the stores file onto the canvas and check store_id = store_id.
  4. Select a noodle and open Performance Options. Leave the defaults: Cardinality Many to Many and Referential Integrity Some records match. Change them only when you know the data, for example One store per many orders with all records matching. Wrong settings here give wrong numbers fast.

Create Sales in the orders table with Analysis > Create Calculated Field:

[Quantity] * [Unit Price] * (1 - [Discount])

Check: Region on Rows and Sales on Text gives four regions. Products and stores were never copied into the orders rows; Tableau joined them for this view only.

2. Add targets as a branch off stores

  1. Drag the targets file onto the canvas and drop it on the stores table, not orders. Check store_id = store_id.
  2. New sheet. Drag Store Id from the stores table to Rows. Each table keeps its own copy of the id and Tableau names the later ones with the table in brackets; the stores copy is the shared one.
  3. Drag Sales and Target Sales to the view.

Each store shows its quarter sales and its quarter target. The targets table has twelve rows per store and the orders table has between 4 and 14. Neither number is multiplied by the other, because Tableau aggregates each table at its own grain before it joins them on store.

3. Make it a multi-fact model

In version 2024.2 and later, the same model can have two base tables:

  1. Remove the targets table from the canvas.
  2. Drag it back and drop it on the New Base Table drop area. Tableau warns that the model will have more than one base table.
  3. Hover over the targets table to show the plus icon and drag it onto the stores table. Stores now has two incoming relationships and becomes a shared table.

The store view from step 2 returns the same numbers. The difference shows when you ask a question across both trees. With two base tables, orders and targets are peers and stores stitches them together. Add a shared date or category table and you can compare by month and category too. In this sample the targets carry category as text and orders get category through products, so there is no shared category table yet. That is a modelling task, not a Tableau setting.

4. Join it the old way and watch it break

  1. Open a new data source with the orders file only.
  2. Double-click the orders table to open its physical layer.
  3. Drag the targets file into that pane. An inner join on store_id appears.
  4. Build the store view again with SUM(Sales) and SUM(Target Sales).

The joined table has 660 rows. Every order row now appears twelve times, once per target row for its store. Every target row appears once per order at that store.

5. Know when a join or blend is still right

  • Join when the result must be one table: an extract filter on a field from both sides, a lookup that is genuinely one to one with every record matching or a union of monthly files. Tableau's own guidance is to use relationships first and joins only when you need them.
  • Blend when the two sources cannot be related, such as two published data sources. Tableau cannot define relationships between published data sources. A blend aggregates the secondary source to the linking fields in the view and left-joins it to the primary. It works, but LODs need the linking field in the view and Workbook Optimizer flags blends for review.

Where this breaks

  • Relating to the wrong table. Drop targets on orders instead of stores and the relationship is between two facts on a non-unique key. Totals may still look right in a store view and go wrong when another dimension is added.
  • Performance Options set to One and All by guesswork. They let Tableau skip work, but if a store id is missing on one side, rows vanish. Set them only after checking.
  • Multi-fact limits. Row-level calculations, combined fields and set definitions can only use fields from the same upstream base table. Tableau's help also notes that Tableau Pulse may not work on multi-fact sources and that swapping dimensions with a parameter can fail silently. Extracts of multi-fact sources need 2024.2.1 or later.
  • Published sources. Relationships cannot be defined between two published data sources. Model inside one published source, or blend.
  • Unmatched rows. With Some records match, a target for a store with no orders is kept on the target side. A physical inner join drops it.

On the brewhouse floor

A brewery has brew logs at batch grain and a sales plan at beer and month grain. Join them and every batch repeats once per plan row, so hectolitres brewed come out several times too high. Nobody spots it until the excise figure disagrees. Relate both to a shared beer table, plus a shared month table in 2024.2 or later. Brewed against planned then lines up per beer per month. The batch stays a batch and the plan stays a plan.
