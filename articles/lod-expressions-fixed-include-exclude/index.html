LOD expressions: FIXED, INCLUDE and EXCLUDE on one store table

Build a store by category table, then use FIXED, EXCLUDE and INCLUDE to answer three questions the view alone cannot. Finish with the filter test that catches most LOD mistakes.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 2 Ankur Napa DesktopLODCertification

Short answer

A level of detail (LOD) expression computes an aggregate at a grain you name, not the grain of the view. FIXED names the grain outright and ignores the view. INCLUDE adds a dimension to the view's grain. EXCLUDE removes one. The part that trips people up is filters: FIXED is computed before ordinary dimension filters, so it ignores them unless you add the filter to context. INCLUDE and EXCLUDE are computed after dimension filters, so they respect them. Know that one sentence and you will get most exam questions on LODs right.

What you will build

One worksheet with Harbour Goods stores and product categories. You will add:

  • a FIXED store total, so each category can show its share of its own store;
  • the same share written with EXCLUDE, to see where the two agree and where they part company;
  • an INCLUDE expression that answers "what does an average product sell in each region?";
  • a Category filter that breaks one of them on purpose.

Before you start

  • Tableau Desktop 2024.2 or later, or Tableau Public (the free desktop app connects to text files too).
  • Three files: the cleaned Harbour Goods orders, the products list and the store registry. The cleaned orders file is the original 60-row sample with its five deliberate faults removed (a duplicate, a blank quantity, a negative quantity, the unknown store ST-099 and the impossible date 31 September). It has 55 orders.
  • Connect: Connect > To a File > Text file, pick the orders file, then drag the products and stores files from the left pane onto the canvas next to it. Tableau relates them on product_id and store_id. It also tidies field names, so store_id shows as Store Id and unit_price as Unit Price. If your version keeps the raw names, use those in the calculations below.

Create the base measure with Analysis > Create Calculated Field, name it Sales:

[Quantity] * [Unit Price] * (1 - [Discount])

Steps

1. Build the store by category table

  1. Drag Store Id to Rows, then Category to Rows to its right. Both are discrete (blue).
  2. Drag Sales onto Text on the Marks card. It lands as SUM(Sales).
  3. Select Analysis > Totals > Add All Subtotals so each store shows its total.

You now have 21 rows. Chennai (ST-007) and Mumbai (ST-011) have only three categories each because neither sold anything in one category this quarter. Missing rows matter later.

2. Add a FIXED store total

Create a calculated field called Store Sales (FIXED):

{FIXED [Store Id] : SUM([Sales])}

Drag it into the view and drop it on the numbers already there. Tableau switches to Measure Names and Measure Values so both columns show. Look at the number Tableau shows for ST-003 Electronics. It says 163,488, which is four times the store's real total of 40,872.

That is not a bug. A FIXED expression returns a value for every underlying row. The default SUM adds it up once per row. ST-003 Electronics has four order rows, so the store total is counted four times. Right-click the pill and change the aggregation with Measure (Sum) > Minimum. Now every ST-003 row shows 40,872.

Make the share:

// Category share of store (FIXED)
SUM([Sales]) / MIN([Store Sales (FIXED)])

Format it as a percentage with one decimal place (right-click the field in the Data pane, Default Properties > Number Format > Percentage).

3. Write the same share with EXCLUDE

// Category share of store (EXCLUDE)
SUM([Sales]) / SUM({EXCLUDE [Category] : SUM([Sales])})

EXCLUDE says: take the view's grain, which is Store Id and Category, drop Category and compute at the store grain. INCLUDE and EXCLUDE results are always measures and are computed for each mark, not each row, so SUM is safe here. Put both shares side by side. They match on every row.

4. Ask an INCLUDE question

Open a new sheet. Put Region on Rows. The question is how much a typical product sells in each region. AVG(Sales) answers a different question, the average order line.

// Average sales per product
AVG({INCLUDE [Product Id] : SUM([Sales])})

INCLUDE adds Product Id to the view's grain, sums Sales per region and product, then the outer AVG averages those product totals within each region.

5. Break it with a filter

Go back to the store table. Drag Category to Filters and keep only Kitchen.

The EXCLUDE share jumps to 100% on every row. The dimension filter ran first, so the store total it divides by is now Kitchen only. The FIXED share stays where it was, because FIXED ran before the filter and still divides by the whole store.

Which one is right depends on the question. "What share of each store is Kitchen?" wants FIXED. "What share of the filtered view is this row?" wants EXCLUDE.

Now right-click the Category filter pill and select Add to Context. The pill turns grey. Context filters run before FIXED, so the FIXED share now reads 100% too.

Where this breaks

  • SUM on a FIXED field. The 163,488 in step 2 is the most common LOD bug in real workbooks. When the FIXED grain is coarser than the view, wrap it in MIN, MAX or AVG, or move the division into the LOD itself.
  • Forgetting the filter order. FIXED ignores dimension filters but respects context, data source and extract filters. A dashboard filter that should change a FIXED number needs Add to Context, or a rewrite as INCLUDE or EXCLUDE.
  • Missing rows. INCLUDE averages only products that sold. A product with no orders in a region is not a zero in the average, it is absent. Pad with a product list if zeros should count.
  • Too many FIXED fields. Each one can add a subquery. Workbook Optimizer flags a high number of LOD calculations for that reason.
  • Unsupported sources. Cubes and a few older connectors do not support LODs at all. Check the source before promising an LOD-based design.

Next on the roadmap

LODs set the grain. Table calculations work on what is already in the view. The exam tests the difference hard: Table calcs: addressing and partitioning. The filter behaviour you saw in step 5 is one slice of the full order of operations.

On the brewhouse floor

A brewery wants each beer's share of the brewhouse output. A FIXED expression on brew date gives the day's total volume, so every batch shows its share of that day. Filter to one beer and the share should stay honest, which is exactly the FIXED behaviour above. INCLUDE on batch answers "how big is an average batch of this beer?" without letting a single 20 hl batch and two 5 hl top-ups pass for three equal brews. The brewery production and yield dashboard uses the same pattern for yield per brew.
