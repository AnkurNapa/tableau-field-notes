Sites, projects and locked permissions

When nobody can say who sees what, the cause is usually permissions set on single workbooks for single users. Measure the sprawl from the repository or Admin Insights, then fix it with groups, locked projects and a short rule book.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 3 Ankur Napa ServerCloudSecurityAPICertification

Short answer

Tableau permissions scale when three rules hold. Grant to groups, never to named users. Set rules on projects, never on single workbooks. Lock the projects that hold production content, so owners cannot quietly widen access. Sites are a harder wall than any of these. Use them only when two audiences must never share users, groups or content.

Permission sprawl is easy to measure. On Tableau Server the repository table next_gen_permissions holds every explicit rule. On Tableau Cloud the Admin Insights Permissions data source shows effective permissions. Count the user-level and workbook-level rules. If they outnumber the project-level group rules, you have the problem this article fixes.

The symptom

A regional sales lead at Harbour Goods sees a margin dashboard meant for finance. Nobody can explain why. The workbook sits in a project called Sales, which gives the Sales group View. Someone also gave her a user-level Allow on the workbook eight months ago for a one-off review. That rule still wins, because user rules are evaluated before group rules. A user Allow beats a group Deny.

Multiply that by a few hundred workbooks and you get the usual audit finding: the site cannot say who has access to what without opening every item.

Measure it

On Tableau Server: the repository

Enable read access to the repository first. It restarts Tableau Server, so do it in a window:

tsm data-access repository-access enable --repository-username readonly --repository-password "<password>"

Connect to the workgroup database on port 8060 as readonly. Then count explicit rules by what they are attached to and who they name:

-- Where do the explicit rules live?
SELECT ngp.authorizable_type,
       ngp.grantee_type,
       COUNT(*) AS rules
FROM next_gen_permissions ngp
GROUP BY ngp.authorizable_type, ngp.grantee_type
ORDER BY rules DESC;

grantee_type is User, Group or GroupAND (a group set). permission is 1 grant to group, 2 deny to group, 3 grant to user, 4 deny to user. Ascending order is increasing precedence.

Now list the rules that cause surprises, user-level grants on workbooks:

SELECT p.name          AS project,
       w.name          AS workbook,
       su.name         AS user_name,
       c.display_name  AS capability,
       ngp.permission
FROM next_gen_permissions ngp
JOIN workbooks w      ON ngp.authorizable_type = 'Workbook' AND ngp.authorizable_id = w.id
JOIN projects p       ON p.id = w.project_id
JOIN users u          ON ngp.grantee_type = 'User' AND ngp.grantee_id = u.id
JOIN system_users su  ON su.id = u.system_user_id
JOIN capabilities c   ON c.id = ngp.capability_id
ORDER BY project, workbook, user_name;

And which top-level projects are not locked:

SELECT p.name,
       p.controlled_permissions_enabled AS locked,
       COUNT(w.id)                      AS workbooks
FROM projects p
LEFT JOIN workbooks w ON w.project_id = p.id
WHERE p.parent_project_id IS NULL
GROUP BY p.name, p.controlled_permissions_enabled
ORDER BY workbooks DESC;

The data dictionary describes controlled_permissions_enabled as whether permissions on workbooks, views and data sources are controlled at the project level. That is the lock. The table does not hold everything: owners, project leaders and admins get capabilities without a row here.

On Tableau Cloud: Admin Insights and the REST API

There is no repository on Cloud. Open the Admin Insights project and connect to the Permissions data source, which holds effective permissions for users and content. Build a count of rules by grantee type and content type, the same shape as the first query.

On either platform, the REST API reads a project's default rules. This call returns what new workbooks in a project will inherit:

curl -s "https://<server>/api/3.28/sites/<site-luid>/projects/<project-luid>/default-permissions/workbooks" \
  -H "X-Tableau-Auth: <token>" -H "Accept: application/json"

Use the API version your server supports. 3.28 matches Tableau 2026.1.

Fix it

1. Decide on sites first

Use one site unless you have a reason for a hard wall: a separate legal entity, external partners or a dev site that must never touch production users. Groups, users and content do not cross sites. Every extra site doubles the admin work.

2. Name groups by job and access level

A pattern that survives staff turnover:

GroupGetsWho
Sales - ViewersView on SalesEvery sales user
Sales - AuthorsPublish on SalesAnalysts who publish
Sales - LeadersProject Leader on SalesOne or two owners
Finance - ViewersView on FinanceFinance team

Sync these from your identity provider if you can. SCIM does this on Cloud and on Server 2025.3 and later.

3. Lock production projects

Lock the top-level projects with the REST API so the rule is scripted and repeatable:

curl -s -X PUT "https://<server>/api/3.28/sites/<site-luid>/projects/<project-luid>" \
  -H "X-Tableau-Auth: <token>" -H "Content-Type: application/json" \
  -d '{"project": {"contentPermissions": "LockedToProject"}}'

LockedToProject locks the project and its nested projects. LockedToProjectWithoutNested locks only the parent. ManagedByOwner is the default and lets owners set their own rules. In the web interface the same setting is Asset permissions: Locked or Customizable.

4. Set the group rules once

Apply the templates at project level. Workbook templates run View, Explore, Publish, Administer, each including the one before. Project templates are View and Publish. Set All Users to None on every locked project, not Denied. None leaves room for a group to grant. Denied blocks everyone in All Users, which is everyone.

5. Remove the strays

Locking a project replaces the workbook-level rules with the project's. Export the stray user rules from the second query first, so you can answer "I used to see that" with evidence.

Prove it

Run the first query again after the change. On a site like the one in the symptom, the before and after might look like this. These figures are illustrative, not measured:

Rule typeBeforeAfter
Workbook rules naming a user4120
Workbook rules naming a group1,2300
Project rules naming a group9664
Top-level projects locked1 of 98 of 9

The number that matters is the first one. Zero user-level workbook rules means access can be explained from the group list and the project tree alone.

Where this breaks

  • The sandbox. People need somewhere to try things. Leave one project customisable, with personal nested projects. Keep production data sources out of it.
  • Owners still own. In a locked project, a content owner loses Set Permissions but keeps the other capabilities on their content. Transfer ownership when people leave.
  • Nested projects inherit the stricter rule. A nested project under a locked parent ignores its own setting.
  • Group sets. A group set grants only to users in every group in the set. Useful for "Sales and Region West". Confusing if nobody wrote down why it exists.
  • Admin Insights is Cloud only. On Server, use the repository and the built-in admin views.

On the brewhouse floor

A winery's site has the same drift. The winemaker gave the cellar hand access to the barrel-ageing dashboard for one blending trial. Two vintages later he can still see grower contract prices on the same workbook. Lock the Cellar project, grant the cellar team View through a group and keep grower pricing in a separate Commercial project. The barrel data still flows to the people topping up barrels. The prices stay with the people negotiating them. See a cellar and barrel-ageing inventory dashboard for the dashboard in question.
