Row-level security that holds

Give each Harbour Goods manager only her own stores' rows. Build it with an entitlement table and USERNAME() on a published data source, then see the same rule as a data policy on a virtual connection.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 2 Ankur Napa ServerCloudSecurityCertification

Short answer

Row-level security (RLS) means two people open the same view and see different rows. In Tableau the reliable pattern has three parts. An entitlement table says which user may see which store. A calculated field compares that table to USERNAME(). That calculation becomes a data source filter on a published data source, so no workbook author can remove it.

If your edition includes Data Management, a data policy on a virtual connection does the same job one layer lower. The policy runs on the server for every query, whatever tool asked. Tableau recommends it in most situations. The published data source pattern needs no extra licence and works on both Tableau Server and Tableau Cloud.

What you will build

A published data source, Harbour Orders (secured), where:

  • a store manager sees one store
  • a regional manager sees the stores in her region
  • three head office users see all six registered stores
  • anyone not in the entitlement table sees nothing

You need two files: the orders harbour-goods-orders.csv and a new entitlement table, harbour-goods-entitlements.csv. The entitlement file has 42 rows and three columns: user_name, store_id and role. It is a deep entitlement table: one row per user per store. The 25 user names are role accounts on a made-up domain, such as storemgr.st014@harbour.example and regmgr.west@harbour.example.

Before you start

  • Desktop signed in to your Server or Cloud site, with a Creator site role.
  • Test users. To prove it on the server you need users whose usernames match rows in the file. On Tableau Cloud the username is the email address. On Tableau Server it depends on your identity store. Either add a few test users with matching names, or edit three rows of the file to match users you already have.
  • For the data policy section only: Data Management on your site. It comes with Tableau Enterprise and Tableau+. Check with your site admin.

Steps

1. Join the entitlement table

  1. Connect to the orders CSV. On the Data Source page, double-click the orders table to open the physical layer.
  2. Add the entitlements CSV as a second connection in the same data source and drag it next to orders.
  3. Set an Inner join on Store Id = Store Id.

An inner join is deliberate. Orders with no entitlement row, such as the ST-099 order, drop out. Nobody is entitled to an unknown store, so nobody should see it.

The join multiplies rows. Each registered store has seven users who may see it, so 59 orders become 413 rows before the filter. The filter brings each user back to one row per order.

2. Write the security calculation

Select Analysis > Create Calculated Field, name it RLS Store Access and enter:

USERNAME() = [User Name]

If your identity store mixes upper and lower case, compare LOWER(USERNAME()) = LOWER([User Name]) instead. It costs a little speed and saves a confused morning.

3. Make it a data source filter

  1. Select Data > Harbour Orders > Edit Data Source Filters.
  2. Select Add, choose RLS Store Access and tick True.
  3. Select OK.

Desktop now shows nothing, because your Desktop username is not in the table. That is the right result. Fail closed.

4. Hide the scaffolding

Right-click User Name and Role and select Hide. Hide RLS Store Access too. Authors should not build on the security fields.

5. Extract and publish

  1. On the Data Source page choose Extract, then save the workbook so the extract builds.
  2. Select Server > Publish Data Source > Harbour Orders.
  3. Name it Harbour Orders (secured) and pick a project.
  4. Leave the data source filter in place. Publishing keeps it with the source.
  5. Select Publish.

6. Set the data source permissions

On the published source, open ... > Permissions. Give the manager groups View and Connect. Deny Download Data Source. A downloaded copy of an extract carries every row, filter or not.

7. Build a test view

Connect a new workbook to the published source. Put Store Id on Rows as a discrete (blue) pill and SUM(Net Sales) on Columns, with this calculation:

[Quantity] * [Unit Price] * (1 - [Discount])

Publish it to the same project.

Check it worked

Sign in to the site as each test user and open the test view. The numbers below come from the sample files:

Head office sees 59 rows, not 60. The missing one is ST-099 for 854.05. That is the inner join doing its job. It is also the first thing a finance user will notice. Decide now whether unknown stores belong to a head office entitlement or to a data quality report.

In Desktop you can preview as another user once you are signed in to the server. The control sits in the status bar and its label may read Filter as User. Preview is a help, not proof. Sign in as the real user at least once.

The same rule as a data policy

With Data Management you can move the rule into a virtual connection, so every workbook, Prep flow input and API query inherits it.

  1. Create a virtual connection to the source that holds both tables. Add the orders and entitlements tables.
  2. On the Data Policies tab, drag orders to Add as Policy Table.
  3. Drag entitlements to Add as Entitlement Table, or choose Use as entitlement table from its menu.
  4. Map the orders store_id column to the entitlement store_id column.
  5. Write the policy condition:
USERNAME() = [user_name]
  1. Use Preview as User to test, then publish the virtual connection. On the Tables tab, turn off visibility for the entitlement table so nobody builds on it.

Tableau's own examples show the shape of other conditions: [Region] = "North", FULLNAME() = [EmployeeName] and ISMEMBEROF('Managers') OR USERNAME() = [employee_name]. The last one lets a group see every row while everyone else sees their own.

Where this breaks

  • Desktop is not the server. In Desktop, USERNAME() returns your local or network login. Only the server returns the signed-in Tableau user.
  • Workbook user filters. A user filter inside a workbook protects nothing if the viewer can edit or download the workbook. Put the filter on the published data source or in a data policy.
  • Download Data Source. Leave it allowed and someone downloads the full extract. Deny it.
  • Usernames drift. A rename in the identity store makes a manager see nothing overnight. Feed the entitlement table from the HR or identity system, not a hand-kept sheet.
  • Row explosion. A deep entitlement table joined to a big fact table can make an extract huge. For thousands of users, look at a sparse design (one row per user per region or group) or a data policy.
  • USERATTRIBUTE() needs a token. It only returns values when the attribute arrives in a JWT, SAML response or OIDC claim. It returns NULL in Desktop authoring and does not work through Tableau Bridge.
  • Flow outputs. Data policies apply to flow inputs, not flow outputs. Anyone who can read a flow's output sees all of it.

On the brewhouse floor

A brewery with two sites has the same need with tanks instead of stores. Build an entitlement table of brewer to fermentation vessel, join it to the tank log and filter on USERNAME(), so each shift brewer sees only the vessels on her site. The head brewer gets every row. A tank with no owner, the old FV-09 that got moved and never relabelled, quietly disappears from every view, which is exactly the conversation you want to have before an audit rather than during one.
