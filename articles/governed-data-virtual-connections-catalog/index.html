Governed data at scale: virtual connections, policies and Catalog

A design guide for Tableau data governance: where virtual connections, data policies, Prep flows, certification and Catalog lineage each belong, what licence each needs and the leak most designs miss.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 4 Ankur Napa PrepSecurityServerCloudCertification

Short answer

Governed data in Tableau is four layers. Each answers a different question. A virtual connection answers "who holds the database credentials?" with "one place, not forty workbooks". A data policy on that connection answers "who sees which rows?" once, for every workbook, data source and flow that uses it. Certification answers "which source should I use?" with a badge. Tableau Catalog answers "what breaks if this column changes?" with lineage. Prep flows sit between them, shaping data before it is certified.

Three of those four need Data Management: virtual connections, data policies and Catalog. Certifying a published data source does not. Data Management is no longer sold as an independent add-on. You have it if your organisation bought it earlier, or through the Tableau+ bundle or Tableau Cloud+ on Cloud, or Tableau Server+ or Tableau Enterprise on Server. Confirm that before you draw anything.

The leak most designs miss: data policies filter the rows a flow reads, but not the rows it writes. A flow output is not filtered by the policy. Anyone who can open that output sees all of it.

The decision

The first choice is where row-level security lives. Each option is a real option; the question is which failure you prefer.

ApproachWhere the rule livesStrengthsWeaknessesNeeds
Data policy on a virtual connectionThe connection, onceOne rule for every workbook, data source and flow input; works for live and extractRequires Data Management; flow outputs escape it; one more object to ownData Management
User filter calculation in a published data sourceEach published data sourceNo add-on; familiar to every CreatorRepeated per source; a new source without the filter leaksNothing extra
Security in the database (views or native row security)The warehouseHolds for every tool, not just TableauNeeds per-user database identity or impersonation; harder with extractsDatabase support
Separate extracts per audience from PrepOne output per audienceSimple to reason aboutCopies multiply; every new region is a new output and schedulePrep Conductor to schedule

My default for an estate with Data Management: policies on virtual connections for anything sensitive, certified published data sources on top for analysts and database security kept for data that other tools also read.

The second choice is where shaping happens:

Shape inWhen it fits
The warehouse (views, dbt models, stored procedures)Logic many tools need; large volumes; a data engineering team exists
A Prep flow on a scheduleLogic only Tableau users need; analysts own it; volumes a flow can handle nightly
The published data source (calculations, relationships)Light logic and definitions; no new physical table needed

Reference design

Harbour Goods, 50 stores, one cloud warehouse, Tableau Cloud with the Tableau+ bundle.

Two published data sources, on purpose. Harbour Sales sits directly on the virtual connection, so the policy follows every query; that is the one most people use. Harbour Orders is the flow output, full of rows the policy never filtered, so it lives in a locked project that only the finance group can open.

An example policy condition, using an entitlement table that maps each user to the stores they may see:

ISMEMBEROF("Harbour Finance")
OR [username] = USERNAME()

Here [username] is the column in store_access and the policy maps store_id in the data tables to store_id in the entitlement table. Keep the entitlement table in the virtual connection but hidden: hidden tables still work for policy filtering and cannot be used in a viz.

Certification rules for this estate:

  • Data sources: certified by the project owner or a project leader, or an administrator. No Data Management needed.
  • Virtual connections and their tables: certification needs Data Management.
  • Databases, tables and files: certification needs Data Management and Catalog enabled.

Catalog on Tableau Cloud is on by default with Data Management. On Tableau Server, the administrator enables the Metadata API first.

Questions to ask the client

  1. Do you hold Data Management today, through an earlier purchase or an edition that includes it? If not, which design works without it?
  2. Who owns the warehouse credentials now and how many workbooks embed them?
  3. Which tables contain data some users must not see? At row level, column level or both?
  4. Is there a table that maps users to what they may see, or does someone keep it in a spreadsheet?
  5. Which outputs do Prep flows write today and who can open them?
  6. Who certifies a data source and what does certification promise: freshness, reconciliation to finance, an owner on call?
  7. When a warehouse column is renamed, who is told and how do they find out which dashboards break?
  8. Do other tools read the same warehouse tables? If so, should security live in the warehouse instead?
  9. How do users sign in and does USERNAME() return what your entitlement table holds (email address or user name)?

Review checklist

  • Data Management licence confirmed in writing for the site or server.
  • Every sensitive table sits behind a virtual connection with a data policy, or in the database with native security.
  • Entitlement table included in the virtual connection and hidden.
  • Policy tested as at least three users: one in the override group, one with one store, one with none.
  • Every Prep flow that reads a policy table writes to a restricted project, or applies its own filter before the output.
  • Connect permission on each virtual connection given to groups, not individuals.
  • Certified sources have a certification note naming an owner and what was checked.
  • Catalog descriptions on the tables and columns people search for most.
  • Data quality warnings used for stale or deprecated sources and removed when fixed.
  • Lineage checked for one critical dashboard back to the warehouse column before go-live.

Anti-patterns

  • The policy that stops at the flow. A flow reads a virtual connection with a data policy, writes a published data source and lands it in an open project. Every row the policy hid is now visible. Data policies do not filter flow output.
  • Certification as decoration. Half the sources on the site carry the badge and nobody remembers why. Certification without a note and an owner tells users nothing.
  • Forty embedded passwords. Each workbook connects to the warehouse with its own credentials. One password rotation becomes forty broken refreshes. That is the problem virtual connections solve.
  • Policies tested only as the author. The author is usually in the override group, so every test passes. Test as real users.
  • Catalog switched on and never curated. Lineage arrives automatically; descriptions, warnings and labels do not. An empty Catalog is a lineage graph, not a catalogue.
  • Building the design before checking the licence. Data Management changes the answer. Ask first.

On the brewhouse floor

A brewery that sells through distributors usually shares depletion data: how much of each beer each distributor sold to bars and shops. Each distributor should see only its own accounts. The brewery's sales team sees everything. A data policy on a virtual connection, with an entitlement table mapping each distributor's users to their territories, enforces that once for every dashboard. The flow that builds the monthly volume summary must not land in a project distributors can open, because its output escapes the policy. The depletions and sell-through dashboard is the kind of view that sits on top.
