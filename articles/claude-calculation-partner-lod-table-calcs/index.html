Claude as your calculation partner: LODs, table calcs and the check

Use Claude in a chat window to write and explain a row-level calculation, a FIXED LOD and a running total on the Harbour Goods orders, then catch the answer that looks right and is not.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 1 Ankur Napa ClaudeAILODTable calcsDesktop

Short answer

Claude is good at Tableau syntax and good at explaining why a calculation does what it does. It does not see your data, your filters or your view, so it guesses at the parts it cannot see. The working pattern is simple: give it the exact field names and the question, paste its calculation into Tableau, then compare the result with a number you worked out another way. In this build Claude's average order value formula is syntactically perfect and wrong for one store. Only the check finds it.

Claude runs in a browser tab or the Claude app here. It is not inside Tableau Desktop. Tableau's own in-product assistant is Tableau Agent, which is a different tool covered in the Level 2 step.

What you will build

One worksheet with Store Id on Rows and four calculations: Net Sales, Share of Company Sales (a FIXED LOD), Average Order Value and a running total by month (a table calculation). Each one comes from a prompt to Claude and each one gets a check.

The data is the shared Harbour Goods orders file: harbour-goods-orders.csv. It has 60 rows from July to September 2026 with the fields order_id, order_date, store_id, product_id, quantity, unit_price and discount. Tableau shows them as Order Id, Order Date, Store Id and so on. The file is deliberately a little dirty: one order appears twice, one has no quantity, one has a negative quantity, one belongs to an unknown store (ST-099) and one is dated 31 September. Leave all of that in. It is what makes the checks worth doing.

Before you start

  • Tableau Desktop or Tableau Public, any recent version.
  • Claude on claude.ai or the Claude desktop app. Any plan works for this.
  • Connect to the CSV: Connect > To a File > Text file. Check that Order Date is a date and Quantity, Unit Price and Discount are numbers.

Steps

1. Give Claude the context once

Start a new chat and paste this first. Field names in square brackets are what Claude will copy back into formulas, so spell them exactly as Tableau shows them.

I am building calculated fields in Tableau Desktop. My data source is one CSV
of retail orders, one row per order line. Fields as Tableau shows them:
[Order Id] string, [Order Date] date, [Store Id] string, [Product Id] string,
[Quantity] integer, [Unit Price] number in rupees, [Discount] decimal where
0.05 means 5 per cent.
Rules: give me Tableau calculation syntax only, say whether each result is
row level or aggregate. Tell me which filters it ignores.

2. Net Sales, a row-level calculation

Write a calculated field called Net Sales: quantity times unit price less the
discount.

A typical reply, abridged:

// Net Sales: row level
[Quantity] * [Unit Price] * (1 - [Discount])

Claude adds that a row with a null Quantity returns null and SUM ignores it. That is correct and worth knowing. Select Analysis > Create Calculated Field, name it Net Sales, paste the formula and select OK.

Check. Drag Net Sales to Text on the Marks card with nothing else in the view. SUM(Net Sales) should read 156,269.85. If you see 155,720.85 you have removed the duplicate order already; if you see 157,367.85 the negative quantity has been filtered out somewhere.

3. Share of company sales, a FIXED LOD

I want each store's share of total company net sales. The denominator
must not change when someone filters out stores. Write it.

A typical reply:

// Share of Company Sales: aggregate
SUM([Net Sales]) / MIN({ FIXED : SUM([Net Sales]) })

Claude explains that { FIXED : ... } with no dimension is a table-scoped LOD. It returns one company total on every row. MIN collapses it back to one value per mark. It also says FIXED ignores dimension filters unless they are context filters. Format the field as a percentage.

Check. Drag Store Id to Rows and the new field to Text. ST-003 shows 25.45% and the seven rows sum to 100%. Now drag Store Id to Filters and untick ST-099. The six remaining shares sum to 99.45%, not 100%. That is the FIXED LOD doing exactly what Claude said: ST-099's 854.05 stays in the denominator because the filter ran after the LOD. If you want the shares of the six real stores to add up to 100%, right-click the Store Id filter and select Add to Context. Context filters run before FIXED. ST-003 becomes 25.59%.

Both answers are right. They answer different questions. You only see the difference because you added up the column.

4. Average order value, where Claude gets it wrong

Write Average Order Value per store: net sales divided by number of orders.

A typical reply:

// Average Order Value: aggregate
SUM([Net Sales]) / COUNT([Order Id])

It is valid. It is also the mistake. COUNT counts rows. This file has one row per order line, so any order that appears on two rows counts twice. Claude had no way to know that HG-40017 is in the file twice. The prompt said "one row per order line" and it took the words literally.

Check. Add two more measures beside the calculation: drag Order Id to Text and set it to Measure > Count, then again as Count (Distinct). Compare the columns for each store.

Pune (ST-014) is the only store where the two counts differ. Go back to Claude with the evidence:

COUNT([Order Id]) is 13 and COUNTD([Order Id]) is 12 for store ST-014.
Order HG-40017 appears twice with identical values. Fix the calculation and
tell me what else the duplicate breaks.

The useful reply switches to COUNTD([Order Id]) and then points out the real problem: SUM(Net Sales) still includes the duplicate 549.00, so even the corrected average is high. The honest AOV for Pune is (32,714.75 - 549.00) / 12 = 2,680.48. No calculation removes an identical duplicate row cleanly. It belongs in the source or in a Prep flow. ST-011 has a quieter version of the same issue: order HG-40056 has no quantity, so it counts as an order with zero sales.

5. Running total by month, a table calculation

Line chart: continuous month of Order Date on Columns, Net Sales on Rows.
I want a running total of net sales across the months. Give me the
calculation and the Compute Using setting.

A typical reply:

// Running Net Sales: table calculation
RUNNING_SUM(SUM([Net Sales]))

with Compute Using set to Table (across), because the months run left to right. Create the field, drag it to Rows in place of Net Sales and select Edit Table Calculation on the pill to confirm the direction.

Check. The points read 68,683.50 for July, 112,645.10 for August and 153,370.85 for September. The grand total from step 2 was 156,269.85. The gap is exactly 2,899.00, which is order HG-40059 dated 2026-09-31. That date does not exist, so it has no month and drops off the axis. Tableau shows a small null indicator at the bottom right of the view to tell you. Claude could not have known. The running total is right; the data is not.

For month-over-month change, the quick table calculation Percent Difference on SUM(Net Sales) gives -35.99% for August and -7.36% for September.

Where this breaks

  • Claude cannot see filters or pills. Say which filters exist and whether they are in context. LOD answers change with that one fact.
  • Wrong field names compile into errors, or worse, into a different field. Paste the exact names from the Data pane.
  • Compute Using is a layout question. The same RUNNING_SUM is right across and wrong down. Tell Claude where the dates sit, or check with Edit Table Calculation.
  • It will explain confidently either way. Ask it to explain your existing calculation in plain words; if its explanation does not match what the view shows, trust the view.
  • Never paste confidential rows. Field names and a few made-up values are enough. If your organisation has rules about AI tools, they apply here too.

Next on the roadmap

Put the LOD and table calc ideas on firmer ground in the Desktop track, then try Tableau's own assistant in Tableau Agent and Explain Data. When you want Claude to query Tableau directly instead of guessing, move to Connect Claude to Tableau with MCP.

On the brewhouse floor

Ask Claude for average volume per brew and it will divide total hectolitres by the count of rows in the brew log. If a brew was logged twice, once at knockout and once after a correction, the average drops and nobody notices. The same COUNT against COUNTD column catches it in thirty seconds. The model sees the rows; the brewer knows brew 412 was typed in twice on a busy Friday. My depletions and sell-through dashboard leans on the same LOD and table calc habits.
