Embedded analytics as a product: a multi-tenant design guide

How to design Tableau embedded analytics for many customers at once: site per tenant or shared site, row-level security with user attributes or entitlement tables, connected apps with on-demand access and the user-based or usage-based licence decision.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 4 Ankur Napa EmbeddingCloudSecurityAPI

Short answer

Multi-tenant embedding is four decisions and they interlock. Isolation: one site per tenant, or one shared site with row-level security. Row-level security: user attribute functions fed from the JWT, an entitlement table, or both. Identity: a connected app that signs your users in, ideally with on-demand access so you stop provisioning thousands of Tableau users. Licensing: per-user Viewer licences or usage-based licensing metered in analytical impressions. Pick the licence and the security model first. The site layout follows from them, not the other way round.

My default for a product with many small tenants on Tableau Cloud: one shared site, one published data source with an entitlement table, user attributes in the JWT for anything the entitlement table cannot express, one connected app per environment and on-demand access. Site per tenant earns its cost only when a tenant contractually needs separate content, admins or data.

The decision

The worked example: Harbour Goods, a retailer and distributor, wants a supplier portal. Each of its 120 suppliers sees sell-through for its own products in Harbour's stores, embedded in the portal suppliers already use. Some suppliers want to see by store, some only by region. A few large suppliers want their own custom dashboards.

Reference design

For Harbour's supplier portal, on Tableau Cloud:

How the pieces fit:

  1. One site per environment, not per tenant. harbour-embedded-dev, -test and -prod, each with its own connected app and secret. Content moves between them by script, as in Automate with Tableau Server Client.
  2. Tenant comes from your app, never from the browser. The portal resolves the signed-in user to a supplier and writes supplier_id into the token on the server. A URL parameter or a viz filter is not security.
  3. On-demand access. The token carries https://tableau.com/oda set to "true" and the group name. Users do not have to exist on the site beforehand. Check the licence prerequisite: the docs name the Embedded Analytics or capacity-based Viewer licences.
  4. User attributes in workbook data sources. On Tableau Cloud, user attribute functions do not work in published data sources. Put the filter calculation in the workbook's data source and keep a published data source underneath for the shared model. Enable Settings > Authentication > Enable capture of user attributes in authentication workflows.
  5. An entitlement table as the audit trail. Even with JWT attributes, keep a table of who may see which supplier. The portal reads it to mint tokens. When someone asks "who could see supplier S-042 in March", you have an answer.
  6. Bespoke tenants get a project. The two suppliers with custom dashboards get their own locked project and group. Everyone else shares one workbook.
  7. Least scope. The connected app applies to the portal projects only and its allowlist names the portal domain only. A leaked secret then embeds nothing else.

Questions to ask the client

  • How many tenants now? How many in two years? How many viewers per tenant? How often do they look?
  • Does any contract require separate storage, separate admins or a named region for one tenant's data?
  • Who decides what a user may see? Where is that decision stored today?
  • Do tenants need to author or edit, or only view? Authoring changes the scope (tableau:views:embed_authoring) and the licence.
  • Are viewers inside your organisation or outside it? Usage-based licensing is for external viewers.
  • What identity provider does the portal use? Can its team mint and sign a JWT on the server?
  • Which browsers and devices must the embed work on, including locked-down corporate ones?
  • Do tenants need exports, subscriptions or Pulse metrics? Under usage-based licensing these count as impressions.
  • What happens when a tenant leaves: how fast must their access end and their content go?
  • Who supports a supplier who says "the numbers are wrong"? Can that person see what the supplier sees?

Review checklist

  • The JWT is minted on the server; no secret reaches the browser.
  • Tokens expire in ten minutes or less, carry a fresh jti and use scp, not scope.
  • The connected app is enabled only in the environment it belongs to, scoped to the right projects, with a strict domain allowlist.
  • A secret rotation has been rehearsed using the second secret slot.
  • Row-level security is applied in the data, not by a filter a user can change.
  • A test user for tenant A has tried to see tenant B by editing URLs, filters and parameters. It failed.
  • User attribute functions sit in workbook data sources if the site is Tableau Cloud.
  • Every embedded view was checked after embedding, since attribute functions do not preview in authoring.
  • The entitlement table or token log can answer "who could see what, when".
  • Licence model confirmed in writing, including how exports and subscriptions are counted.
  • Offboarding a tenant is a script that has been run once in test.
  • Usage is monitored per tenant, from Admin Insights or the impressions summary.

Anti-patterns

  • One shared service account for every viewer. Every tenant sees the same data unless you filter in the page. Tableau logs every view as one person. Audit is gone and RLS is impossible.
  • Tenant ID in the URL. ?supplier=S-042 on the embed URL is a filter, not security. Anyone can change it.
  • Site per tenant by default. Two hundred sites means two hundred copies of every workbook, every fix published two hundred times and drift by the third month.
  • The secret in front-end code. Anything in the browser is public. Minting a token in JavaScript hands out the ability to be any user.
  • RLS in a published data source that uses user attribute functions on Cloud. It is not supported there. It fails quietly in authoring previews and someone ships it.
  • Choosing the licence after the build. Usage-based licensing changes how exports, subscriptions and API calls cost you. Design the features with the meter in view.
  • Tableau Server topology copied from an internal deployment. Embedded load is spiky: a portal email to every supplier on Monday morning. Size for the burst, or choose Tableau Cloud and let that be someone else's pager.

On the brewhouse floor

A brewery that supplies two hundred bars can run the same design. Each bar's manager sees their own depletions and keg returns inside the ordering portal; the regional distributors see their territory; the brewery's sales team sees everything. One shared site, one workbook, an entitlement table keyed on account number and a token that says which account is asking. The day a bar changes hands, one row changes and the new owner sees nothing from before the sale. My depletions and sell-through dashboard is the kind of view that sits at the centre of it.
