Prep at scale: faster flows, parameters and version control

Find which flow is slow and why, cut the rows and fields it reads, replace six copies of one flow with a parameter and keep flows reviewable outside the server.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 3 Ankur Napa PrepPerformanceAPI

Short answer

Slow Prep flows are almost always slow for one reason: they read more than they use. A flow that pulls every column and every year from a database, then filters to one region in the third step, has paid for the whole table before the filter runs. Measure first, with the Performance of Flow Runs admin view or the REST API's flow run times. Then fix in this order: fewer fields, fewer rows at the input, aggregate before you join and push heavy work into the database. When you find six copies of one flow that differ only by region or file name, collapse them into one flow with a parameter. And keep every flow somewhere you can see who changed what, because a flow edited on the web leaves no trace in your laptop's copy.

The symptom

Harbour Goods has grown. The nightly flow that built Harbour Orders from one PostgreSQL table now reads three years of orders for 50 stores. Its scheduled task used to finish in a few minutes. Now it runs past 06:00 and the regional dashboards open with yesterday's numbers missing. A second complaint arrives the same week: someone fixed a store mapping in the North copy of the flow and forgot the five other regional copies.

Two problems, one cause each. The flow reads too much. And there are six flows where there should be one.

Measure it

Do not guess which step is slow. Measure the run, then the parts.

Run history. On Tableau Server or Tableau Cloud, a site administrator can open the Performance of Flow Runs admin view. It shows the history of every flow run on the site and filters by flow name, output step, owner, run type and start time. Backgrounder Task Delays shows how long tasks waited before they started, which tells you whether the flow is slow or just queued behind extract refreshes. Background Tasks for Non Extracts counts successes and failures.

The REST API. To track run times over weeks, pull them yourself. The Get Flow Runs method (API 3.10 and later) returns each run's startedAt, completedAt and status:

curl -s "https://<your-pod>.online.tableau.com/api/<api-version>/sites/<site-id>/flows/runs?filter=flowId:eq:<flow-id>" \
  -H "X-Tableau-Auth: <token>" -H "Accept: application/json"

Subtract startedAt from completedAt per run and you have a duration series. Plot it in Tableau, naturally.

The flow itself. Open the flow in Prep Builder and look at each Input step:

  • How many fields are ticked in the Input pane? Every field you read is a field you pay for, used or not.
  • Is there a filter in the Input step, or does the first filter sit two steps later?
  • Is the input a whole table when a custom SQL query or a view would return a tenth of it?
  • Does a Join step join two detailed tables before an Aggregate step summarises them?

Write down the run duration before you change anything. Without a before number there is no after.

Fix it

1. Read fewer fields

In each Input step, untick every field the flow does not use. On a wide orders table this is often half the columns. Removing a field in a later Clean step does not help as much, because the input has already read it.

2. Read fewer rows

Filter as early as possible, ideally in the Input step itself, so the condition reaches the database. If the dashboards only show the last 24 months, say so:

[order_date] >= DATEADD('month', -24, TODAY())

For heavy logic, a custom SQL input or a database view does the work where the data lives. The database is usually better at joining two large tables than a flow is.

3. Aggregate before you join

If a daily summary per store is all the output needs, aggregate the orders to store and day first, then join the store table. Joining 50 store rows to a few thousand daily rows is cheap. Joining them to millions of order lines and then aggregating is not.

4. Separate design-time speed from run-time speed

The data sample setting in the Input step changes how many rows Prep shows you while you build. It makes editing faster. It does not change what the scheduled run reads: a run always processes the full data. Do not mistake a snappy editor for a fast flow.

5. Replace the copies with a parameter

Flow parameters work in Prep Builder 2021.4.1 and later and on Tableau Cloud and Server 2021.4.0 and later.

  1. Select the parameter icon on the top menu, then Create Parameter.
  2. Name it p_region, type String and under allowable values choose a List: North, South, East, West. Set the current value to North.
  3. In the filter after the store join, insert the parameter from the editor's parameter list rather than typing it. The condition reads like this:
[region] = [p_region]
  1. In the Output step, add the parameter to the published data source name, such as Harbour Orders North for the North run, so each run writes its own source. Output names accept parameters; use the parameter option beside the name field rather than typing the brackets.
  2. Publish once. Create four scheduled tasks on the same flow, each with a different p_region value set in the task.

An administrator must enable flow parameters in the site or server settings before parameterised flows can run or be scheduled on the web. Avoid All as the allowed values for any parameter used in a custom SQL input or a database output: a free-text parameter in custom SQL is an injection risk and the help says so.

From Prep Builder 2023.2 there are also system parameters for the run date and time, usable in output file names and published data source names. They are handy for dated snapshot files.

6. Put the flow under version control

Published flows keep a revision history on the server and you can restore an earlier version from the flow's page. That covers rollbacks. It does not give you review, or a diff, or a record of why something changed.

For that, keep the .tfl in Git next to the scripts that deploy it. A .tfl is a zip archive of JSON files. Tableau does not document the format, but community tools rely on it and unzipping it lets you diff two versions as text. Three habits make this work:

  • One person downloads the published flow before editing, so web edits are not lost.
  • Every change goes through a pull request with the before and after run time in the description.
  • Publishing is done by a script (Tableau Server Client or the REST API), not by hand, so the published flow always matches a commit.

Prove it

These numbers are illustrative, not measured. They show the shape of the change you should expect and the evidence to collect.

Aggregate before jointwo thirds1112 minutes

Collect yours from the Performance of Flow Runs view or the REST API for at least five runs before and five after. One fast run after a change proves nothing; the database might have been quiet that night.

For the parameter change, the proof is a count: six flows down to one flow with four tasks and the next store mapping fix made once.

Where this breaks

  • Custom SQL hides intent. A query in an Input step is opaque to anyone reading the flow. Name it, comment it in the description and keep it in Git.
  • Parameters cannot vary everything. They work in file paths, table names, custom SQL, filters, calculated fields and output names. They cannot add or remove steps. Two regions that need different logic need two branches, not a parameter.
  • Linked tasks hide slow runs. In a linked task, a slow first flow delays every flow after it. Check each flow's own duration, not just the chain's.
  • Version history is not version control. Restoring an old version on the server does not tell you what changed. Keep the diff somewhere a human can read it.
  • The database pays. Pushing work upstream makes the flow faster and the database busier. Tell its owner before you move a heavy join into a view at 02:00.

On the brewhouse floor

A distillery that runs three stills often ends up with three copies of the same spirit-yield flow, one per still, each with its own fix applied or forgotten. One flow with a still parameter and three scheduled tasks puts the litres of pure alcohol per tonne of grain on the same definition for every still. Filter to the current season at the input and the flow stops rereading ten years of runs every night. The distillery production and spirit-yield dashboard then compares stills that are measured the same way.
