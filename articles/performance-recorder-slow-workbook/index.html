Fix a slow workbook with the Performance Recorder

Record a slow dashboard, read the events that cost the time, fix the three usual culprits and prove the fix with a second recording, not a feeling.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 3 Ankur Napa DesktopServerPerformance

Short answer

Do not guess why a workbook is slow. Record it. Help > Settings and Performance > Start Performance Recording in Tableau Desktop logs every query, layout pass and render while you use the dashboard, then opens a workbook that shows where the seconds went. In most slow workbooks one of three things owns the time: a query that asks the database for too much, filters that each fire their own query or a view with so many marks that layout and rendering crawl. Fix the biggest bar, record again and keep both recordings. That pair of numbers is what gets a fix accepted.

The symptom

The Harbour Goods regional sales dashboard takes long enough to open that store managers export to a spreadsheet instead. It has six worksheets on one dashboard, eight quick filters, a store and order detail table. It connects live to the sales database. Every filter change spins for a while.

The sample files in this article are small, so they will not be slow on your laptop. The method is the same on 55 rows or 50 million. Use the cleaned Harbour Goods orders with products and stores to practise reading a recording, then use it on your own slow workbook.

Measure it

Record in Tableau Desktop

  1. Open the workbook. Close any other workbooks so their queries do not pollute the log.
  2. Select Help > Settings and Performance > Start Performance Recording.
  3. Do exactly what a slow user does: open the dashboard, change two filters, select a mark.
  4. Select Help > Settings and Performance > Stop Performance Recording.

A new workbook opens. Its Performance Summary dashboard has three parts:

  • Timeline: every event in order, so you can see which action triggered what.
  • Events: events sorted by duration, longest first.
  • Query: the query text for whichever event you select.

Event types you will see include Executing query, Compiling query, Computing layouts, Connecting to data source, Generating extract, Geocoding and Blending data. On Tableau Server, Server rendering also appears.

Record on Tableau Server

A server administrator enables Record workbook performance metrics in the site's Settings. Then add :record_performance=yes& to the view URL just before :iid=, refresh and use the view. A performance icon appears in the toolbar and opens the same kind of workbook. Server timings include rendering and network, which Desktop does not. Measure where your users actually are.

Ask Workbook Optimizer

In Tableau Desktop select Server > Run Optimizer. It checks the workbook against guidelines and sorts them into Take action, Needs review and Passed. For a slow dashboard the useful ones are Number of filters, Filter uses "Only Relevant Values", Number of views in a dashboard, Live data connections, Number of LOD calculations, Uses data blending and Dashboard size not fixed. Optimizer reads the design. The recorder measures it. Use both.

Read the recording

Sort Events by elapsed time and ask three questions:

  1. Is the top bar a query? Select it and read the SQL in Query. Look for a query that returns every order row, a filter on a string calculation or a long chain of subqueries from LODs.
  2. Are there many small queries in a row? Eight quick filters set to Only Relevant Values each run their own query whenever another filter changes. Twenty fast queries can cost more than one slow one.
  3. Is the top bar Computing layouts? That is marks. A detail table with every order row, or a map with thousands of points, spends its time drawing, not querying.

Fix it

Fix the largest bar first, then record again. In order of how often they win:

  • Show fewer marks. Replace the order detail table with a summary by store and category. Put the detail on a separate sheet reached by an action. Tableau's own accessibility guidance gives another reason: views over 1,000 marks are rendered on the server.
  • Tame the filters. Switch quick filters from Only Relevant Values to All Values in Database where users will cope. Cut eight filters to the three people use. Replace a filter on a calculated string with a filter on the raw field.
  • Move work out of the query. Turn row-level string and date calculations into fields in the source or in a Tableau Prep flow. Materialise them in an extract.
  • Extract the live connection. If minute-by-minute freshness is not needed, publish an extract refreshed on a schedule. Use Aggregate data for visible dimensions when the dashboard never needs order-level rows. Add extract filters for history nobody reads.
  • Simplify LODs. A FIXED expression at order grain rebuilt on every filter change is a common hidden cost. If the grain is fixed, compute it upstream.
  • Fix the dashboard size. An automatic size means each screen size renders and caches differently. A fixed size lets the server reuse cached views.
  • Use context filters carefully. A context filter that cuts the data hard and rarely changes can speed up a Top N or FIXED. One that changes on every click can slow things down, because the context is rebuilt each time.

Prove it

Record again with the same steps. Compare total time and the top three events.

The table below is illustrative: it shows the shape of a typical before and after on a live warehouse connection, not a measurement from the small sample files.

EventBeforeAfterWhat changed
Executing query, detail table9.8 s0.6 sSummary by store and category, detail on demand
Executing query, quick filters (8)6.1 s0.9 sThree filters, All Values in Database
Computing layouts3.4 s0.5 sAbout 40,000 marks down to under 200
Total to first view21.0 s2.6 sExtract with aggregated data

Put both recordings in the change log for the workbook. When someone says it feels slow again in six months, you have a baseline instead of an argument.

Where this breaks

  • Desktop is not the server. A workbook that is fast on your laptop over a fast network can still be slow for a store manager on a shared Server node. Record where the users are.
  • The first run is cold. Caches make the second open faster. Record a cold open and a warm open and say which is which.
  • The database is the bottleneck. If Executing query dominates after you have trimmed the query, the fix is an index, a summary table or a different source. Take the SQL from the Query view to the database team.
  • One recording, many causes. Change one thing at a time. Five changes and one recording cannot tell you which fix worked.
  • Optimizer flags are not verdicts. A live connection can be the right design. Mark the guideline as ignored with a reason rather than switching blindly.

Next

Fast is half of usable. The other half is whether everyone can read it: Accessible dashboards. Backgrounder load and extract schedules are on the Server track at Level 3 of the roadmap.

On the brewhouse floor

A brewery's fermentation dashboard that plots every sensor reading from every tank, every minute, will crawl. The recording shows it at once: Computing layouts owns the time because forty thousand points are being drawn. Aggregate to the hour for the overview and keep minute data for the one tank someone selects. The brewer wanted to see which tank is running warm, not every reading since Monday. The fermentation monitoring build faces the same trade-off.
