Monitor usage and health

Find out who uses what before the licence renewal finds out for you. Read Admin Insights and the Activity Log on Tableau Cloud, query the repository on Tableau Server and turn the answer into an archive rule.

12 Oct 2026 Tableau as of October 2026 Checked against Tableau Help Level 3 Ankur Napa ServerCloudPerformanceAPICertification

Short answer

Every Tableau site keeps a record of who opened what and when. Where it lives depends on the platform:

  • Tableau Cloud: the Admin Insights project, a set of prepared data sources about your site. It keeps 90 days by default and up to 365 days with Advanced Management. The Activity Log, also part of Advanced Management, streams detailed events to your own Amazon S3 bucket.
  • Tableau Server: the repository, a PostgreSQL database called workgroup, plus the built-in admin views. You read it with SQL once you enable access.

Ask three questions of that record: which content nobody opens, which licences nobody uses and which views are slow. The first answer usually frees the most space and the most attention.

The symptom

The Harbour Goods site has grown to 40 workbooks across five projects. Search returns four versions of the same sales dashboard. Storage keeps rising. The licence renewal is next quarter and finance wants to know why there are so many Creators. Nobody can answer from memory. Nobody should try.

Measure it

On Tableau Cloud: Admin Insights

  1. Open Explore and the Admin Insights project. Site admins see it by default.
  2. Open the Admin Insights Starter workbook for a first look.
  3. For your own analysis, connect to these data sources:
    • TS Events: sign-ins, publishing and view access
    • TS Users: users, site roles and licence details
    • Site Content: projects, workbooks, views and data sources
    • Viz Load Times: how long views take to load
    • Job Performance: extract refreshes and flow runs
  4. Join the questions, not the tables. Count view-access events in TS Events by workbook for the last 90 days. Workbooks in Site Content with no events are your stale list.

Check the refresh time on each data source before you quote it in a meeting.

On Tableau Cloud: the Activity Log

The Activity Log records site events such as set_permissions, content_owner_change, login_authentication and hist_access_view in near real time. Events reach your S3 bucket within about 15 minutes. You need Advanced Management, your own AWS account and a bucket encrypted with a KMS key in the same region as your site. Use it when Admin Insights is too coarse, for example to audit every permission change in a month.

On Tableau Server: the repository

Enable read access. This restarts Tableau Server:

tsm data-access repository-access enable --repository-username readonly --repository-password "<password>"

Connect to database workgroup on port 8060 as readonly. Stale workbooks first:

SELECT w.name                              AS workbook,
       w.project_name,
       w.owner_name,
       ROUND(w.size / 1048576.0, 1)        AS size_mb,
       MAX(vs.last_view_time)              AS last_viewed,
       COALESCE(SUM(vs.nviews), 0)         AS views_all_time
FROM _workbooks w
LEFT JOIN _views_stats vs ON vs.views_workbook_id = w.id
GROUP BY w.id, w.name, w.project_name, w.owner_name, w.size
HAVING MAX(vs.last_view_time) IS NULL
    OR MAX(vs.last_view_time) < NOW() - INTERVAL '90 days'
ORDER BY size_mb DESC;

nviews is a running total per user per view, not a 90-day count. Use last_view_time for staleness and historical_events if you need counts inside a window.

Then licences by role and how many people have not signed in for 90 days:

SELECT licensing_role_name,
       COUNT(*) AS users,
       SUM(CASE WHEN login_at IS NULL
                  OR login_at < NOW() - INTERVAL '90 days'
                THEN 1 ELSE 0 END) AS idle_90d
FROM _users
GROUP BY licensing_role_name
ORDER BY users DESC;

On either platform: the REST API

The REST API returns a total view count per view, which is enough for a quick stale list without database access:

curl -s "https://<server>/api/3.28/sites/<site-luid>/views?includeUsageStatistics=true&pageSize=1000" \
  -H "X-Tableau-Auth: <token>" -H "Accept: application/json"

What the Harbour Goods site showed

I put a 90-day extract of the site's workbook usage in server-workbook-usage.csv. It is synthetic: 40 workbooks with project, owner, views and distinct users in the last 90 days, last viewed date and size. Summed in Python:

  • 16 of the 40 workbooks had zero views in 90 days.
  • Those 16 hold 388.6 MB of the site's 640.6 MB, about 61 per cent.
  • Seven of the 16 sit in Sandbox. Nine sit in production projects.
  • The top five workbooks took 34.7 per cent of all 11,043 views.

That last line is the healthy part. People do use the site. They use a small part of it a lot.

Fix it

  1. Write the archive rule down. Zero views in 90 days means the owner gets a notice. No reply in 14 days means the workbook moves to an Archive project that only admins can open. Thirty days in Archive means deletion, unless someone asks for it back.
  2. Automate the notice. Run the stale-workbook query or the REST call weekly and send the list to each owner. A script is better than a person here, because a person gets tired of being the bad news.
  3. Right-size licences. A Creator who has not published or connected to new data in 90 days is an Explorer in practice. Talk to them before you change the role.
  4. Fix the duplicates. Four versions of one dashboard usually means one certified data source is missing. That is the Level 2 step on published data sources.

Prove it

Re-run the same measures after one archive cycle. On this site, archiving the 16 stale workbooks would take storage from 640.6 MB to 252.0 MB and the workbook count from 40 to 24. Those figures come from the synthetic sample, so treat them as illustrative. Measure your own site the same way.

Track one more number: searches that return more than one workbook with the same name. It should fall to zero in production projects.

Where this breaks

  • Retention. Admin Insights keeps 90 days by default. Server's http_requests table keeps far less. If you want a year of history, copy the numbers somewhere you control each month.
  • Subscriptions hide readers. A dashboard that people read only as a weekly subscription email can show few browser views and still be read every Monday. Check its subscriptions before you archive it.
  • Owners who left. Stale content often belongs to someone who is gone. Reassign ownership before archiving, or the notice goes nowhere.
  • Never write to the repository. Read only. Changing it directly can break Tableau Server and leave it unsupported.
  • Cloud has no repository. Admin Insights and the Activity Log are the substitute. Plan for that before a Server to Cloud move, because every repository query you rely on needs a new home.

On the brewhouse floor

A distillery's reporting site fills up the same way as a warehouse fills with casks nobody has sampled. The maturation dashboard gets copied for each new spirit, the copies stop being opened and nobody deletes them in case the excise auditor asks. Run the stale query, archive what nobody has opened in 90 days and keep the one certified cask inventory source. The auditor wants one number for litres of pure alcohol in bond, not four.
